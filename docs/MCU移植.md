# MCU 移植 —— Victrl 跑在 ESP32-P4 上

> **中文** | [English](MCU-Port.md)

这是本仓库里的那份实现。原型跑在 PC 上；这一版跑在一颗**没有操作系统**的单片机上，而且整个 harness 一并搬了上去。

## 芯片上有什么

| | |
|---|---|
| 板卡 | ESP32-P4——双核 RISC-V，32 MB PSRAM，16 MB flash |
| 运行时 | ESP-IDF 6.0.1 + FreeRTOS。没有 Linux，没有 Python，没有操作系统。 |
| WiFi | ESP32-C6，走 SDIO（ESP-Hosted） |
| 眼睛 | MS2109 USB 采集卡，MJPEG 1920×1080 |
| 手 | TinyUSB 复合 HID——键盘（6KRO，1 ms）+ 绝对坐标鼠标（0…32767） |
| 存储 | microSD（FAT32）：会话、计划、轨迹、任务日志 |
| 界面 | 设备端 WebUI，由板子自己提供 |

以及一切让无状态模型表现得像个 agent 的东西：

- 感知 → 思考 → 执行 状态机
- 轨迹、计划，以及会话（对话窗口）存储
- **状态栏**——光标位置、按住的鼠标键、锁定键状态、屏幕是否变化、输入法切换次数，以及最后一次 `type` 真正发到线路上的那个字符串
- 验证与失败分类
- MJPEG 解码 → 感兴趣区域（ROI）裁切缩放 → 重编码 → base64 管线
- 自适应推理强度，以及逐步延迟埋点

## 这次移植实际付出了什么代价

有意思的不是它塞得进去，而是安全网消失之后*坏掉的是什么*。在 Linux 上的 Python 里，一次 6 MB 的分配、过一会儿再释放，没什么可说的；按字节截断字符串，没人看得见；起一个后台线程，不要钱。这些在这里没有一条成立。

### 硬件解码器不能缩放，也不能裁切

ESP32-P4 的 JPEG 解码器只按画面的原始分辨率输出。就这样，没有例外。由此有两个后果：

1. 解码缓冲区必须按**源**尺寸来分配（再补齐到驱动的 16 字节对齐），而不是按缩小后的目标尺寸。按目标尺寸分配会让每一次解码都以 `JPEG_ERR_NO_MEM` 失败——而调用方会悄悄退回整帧，于是这个功能一直静默地不工作。
2. 更糟的是，等缓冲区足够大之后：把**缩小后**的宽高交给编码器，却喂给它全尺寸像素，编码器就只会去读图像的**左上角那一块**。模型于是看到一张缺了右边和下边的图，而每一个归一化坐标都是偏的。这就是一个静默的、看起来还挺合理的错误答案——最坏的那一种。

所以缩放只能放到软件里做，在整分辨率解码之后。这就诚实地引出了下一个问题：这值得吗？实测下来，值得——裁切加重采样要花约 197 ms，但更小的载荷光是在 base64 这一项上就省下更多（25 ms 对 150 ms），并且让上传量下降 4.7 倍。

### 编解码引擎每一步都在重建

第一版在**每一步**都创建再销毁解码器和编码器引擎，并重新分配一块 6.2 MB 的 PSRAM 解码缓冲区：

```
jpeg_new_decoder_engine()              per step
jpeg_alloc_decoder_mem(1920*1080*3)    per step, 6.2 MB
jpeg_decoder_process()                 per step
jpeg_del_decoder_engine()              per step
free(6.2MB)                            per step
... then the same again for the encoder
```

采集卡在整次运行中给出的几何尺寸是固定不变的，所以这些全部都是不变量。它之所以看不见，是因为整件事被塞进了一个不透明的 `jpeg=180ms` 计时字段里——这也是为什么现在这条管线被埋点成 `setup / decode / resample / encode`。**你没法优化一个已经被你合并成单个数字的东西。**

### 一次静默的截断就能终结一个任务

固定大小的缓冲区加上 `strncpy`/`snprintf("%.Ns")`，是按**字节**截断的，而那个任务的目标是中文。把一个三字节字符切成两半会产生非法 UTF-8，而 JSON 请求体必须是合法 UTF-8——于是 API 用 400 拒掉了整个请求，harness 却把它报成一个通用的 HTTP 失败。那个任务的每一步都失败得一模一样，而真正要紧的证据只在一个地方：存下来的目标末尾是一个替换字符。

修复是刻意做成两层的：每一处都改成按字符安全截断，再加上在每一个请求都会经过的那一个点上做一次 `utf8_sanitize()`，让这个不变量是被*强制执行*的，而不是被*信任*的。

### 同一个 bug，在上层再来一次

那处修好之后请求能通了——可模型还是在第 1 步之后就收工，因为目标在 HTTP 边界上被截断到 255 字节，在一个 `char task[256]` 里。修复已经打在两层上，第三层依旧把用户的指令切成了两半。**被静默缩短的目标是这个项目遇到过的最有破坏性的失败**，因为 agent 会很有信心地完成一个比交给它的更短的任务。现在过长的输入是一个明确的错误。

### 栈和静态缓冲区又变得要紧了

主任务的默认 3.5 KB 栈不够处理会话，直接抛出了一个 `Stack protection fault`。在 Python 里会条件反射地丢到堆上的那些组件数据结构，在这里是栈上或静态分配，而它们的尺寸又反过来决定了那 32 MB 里真正能用的是多少。

### 因为*它是台设备*，才有了这些可能

有三项能力在原型里没有对应物，它们也正是这次移植除了缩小体积之外值得做的原因：

- **感兴趣区域（ROI）放大。** 模型可以要求看某个子区域，harness 会精确地反向映射回去。小目标变得可辨认；上传量下降 4.7 倍。
- **由设备自己断言的状态栏。** 板子是唯一知道指针在哪、屏幕有没有变、锁定了哪些锁定键的一方。它每一步都直接说出来，而不是让模型去推断。
- **失败分类。** 把“从未到达”和“被重新解释”区分开——见[失败分类学](失败分类学.md)。
