# Victrl — 硬件 AI Agent (ESP32-P4)

基于 ESP32-P4 的硬件级 AI 计算机操控器。通过 USB HDMI 采集卡截取屏幕，发送给多模态大模型分析，模型返回动作指令，由设备通过 USB HID（键盘+绝对坐标鼠标）在目标电脑上执行。

**不需要在被控电脑上安装任何软件** — 纯硬件层面的视觉+操控闭环。

---

## 硬件平台

| 部件 | 型号 | 用途 |
|------|------|------|
| 主控 | ESP32-P4 | USB Host(UVC采集)、USB Device(HID输出)、推理调度 |
| 协处理 | ESP32-C6 | WiFi 6 + BLE 5.3，通过 SDIO 与 P4 通信 |
| 采集卡 | MS2109 | HDMI 转 USB，输出 MJPEG 视频流 |
| 屏幕 | NV3007 | 142×428 SPI LCD，横屏状态显示 |
| 按键 | GPIO0/1 | 开始/暂停/终止 |
| 存储 | SD 卡 | FatFS，存放配置、日志、提示词 |

## 状态机

```
IDLE ← GPIO1 长按(终止) ← 任意状态
  │
  ├─ GPIO0 短按 / WebUI start → RUNNING
  │     ├─ GPIO1 短按 → PAUSED
  │     │     ├─ GPIO1 短按 → RUNNING (恢复)
  │     │     └─ WebUI step → STEP → 执行1步 → PAUSED
  │     ├─ WebUI stop / GPIO1 长按 → STOPPING → IDLE
  │     └─ done=true → IDLE
  │
  └─ WebUI start → RUNNING
```

## 主循环流程

1. **采集** — UVC 抓一帧 MJPEG（MS2109 持续流）
2. **压缩** — 硬件 JPEG 编码器降质重压（质量可配）
3. **编码** — Base64 编码
4. **请求** — HTTPS POST 到 DeepSeek Responses API (`/responses`)
5. **解析** — 提取 `output_text` → cJSON 解析动作数组
6. **执行** — 逐条执行 HID 动作（click/move/drag/scroll/press/type/wait）
7. **休眠** — `sleep_before_next`（最低 1s）
8. **循环** — 回到步骤 1

## 支持的动作

| 动作 | 说明 |
|------|------|
| `click` | 有 box_2d=移动到目标再点，无 box_2d=原地点击 |
| `move` | 移动光标到 box_2d 中心 |
| `drag` | from_box → to_box 拖拽，8 步插值 |
| `scroll` | 滚轮 delta_y（横向未支持，见下） |
| `press` / `hotkey` | 按键组合 (mod+key 格式)，两者等价 |
| `type` | 输入 ASCII 文本；`clear_first: true` 会先按 Ctrl+A |
| `run` | **原子启动**：自己做 Win+R → 输入 `command` → 回车，并自检屏幕是否变化 |
| `wait` | 等待 wait_seconds 秒 |
| `release` | 释放指定鼠标按键 |

> `run` 是启动程序的首选动作——一次调用替代模型手搓的四个往返，并且内部会验证
> 命令是否真的执行了（屏幕无变化就再按一次 Enter）。

## 快速开始

### 1. 准备 SD 卡

将 `sdcard/` 目录下全部文件复制到 SD 卡根目录，编辑 `config.json`：

```json
{
  "uvc": {
    "capture_width": 1920,    // UVC 采集分辨率
    "capture_height": 1080,
    "output_width": 1920,     // 被控电脑屏幕分辨率 (HID 坐标映射用)
    "output_height": 1080
  },
  "api": {
    "endpoint": "https://api.deepseek.com/responses",
    "key": "你的 DeepSeek API Key",
    "model_name": "deepseek-flash",
    "timeout": 120,
    "max_retries": 3,
    "max_output_tokens": 16384,
    "enable_thinking": true,
    "reasoning_effort": "high",         // low | high | max
    "upload_max_dim": 1360,             // 上传帧最长边下采样尺寸，0 = 不下采样
    "save_frames": false                // 每步把截图写 SD 卡（约 150-250KB 阻塞写）
  },
  "agent": {
    "max_actions": 100,
    "history_max_len": 10,
    "system_prompt_interval": 0         // 0 = 不轮换，始终用完整提示词（利于前缀缓存）
  },
  "wifi": {
    "ssid": "WiFi 名称",
    "password": "WiFi 密码"
  }
}
```

> `endpoint` 会被**原样当作请求 URL** 使用，所以必须带上 `/responses` 后缀。
> 若网关返回 404，可尝试 `https://api.deepseek.com/v1/responses`。
> `reasoning_effort` 只在 `enable_thinking: true` 时生效；置 false 会强制降为 `low`。
> `upload_max_dim` 默认 1360：模型侧会把超过约 1300×1300 的图等比缩回，且每张图
> 的 token 计费有约 1024 的上限，所以上传更大的图只花带宽、不换来精度。
> `system_prompt_interval` 默认 0（不轮换）。轮换精简提示词省下的 token 极少，
> 却会打断 Responses API 的前缀缓存，不划算。

### 2. 编译烧录

```bash
idf.py build flash monitor
```

### 3. 使用

- **WebUI**: 浏览器访问 `http://<设备IP>`，两个标签页：
  - **Dashboard** —— 任务控制、系统/网络/时间状态、上一步耗时分解、计划、运行日志
  - **SD 卡文件** —— 直接在浏览器里浏览/编辑/新建/删除 SD 卡上的文件
- **按键**: GPIO0 短按开始，GPIO1 短按暂停/恢复、长按停止
- **自动**: 启动后自动连接 WiFi、初始化所有外设；NTP 在后台异步同步

### WebUI 文件管理

不再需要反复拔插 SD 卡。`/sdcard` 下的任何文件都能在浏览器里改：

| 端点 | 说明 |
|------|------|
| `GET /api/fs?path=/sdcard/...` | 目录列表（JSON，目录在前，含大小） |
| `GET /api/fs/read?path=...` | 读取文件（`text/plain`，上限 128KB） |
| `POST /api/fs/write` | `{path, content}` 写入 |
| `POST /api/fs/delete` | `{path}` 删除文件或空目录 |
| `POST /api/fs/mkdir` | `{path}` 新建目录 |
| `POST /api/reboot` | 重启设备（改完 `config.json` 后需要） |

安全约束：所有路径必须落在 `/sdcard` 之内，含 `..` 或 `/sdcardX` 形式的前缀
一律拒绝。**WebUI 本身没有鉴权**，请只在可信局域网内使用。

> 改 `config.json`、系统提示词、甚至 `web/index.html` 都可以直接保存；
> `config.json` 与提示词需要重启或重新开始任务才生效，`index.html` 刷新页面即可。
> 注意：**编辑 `web/index.html` 时如果写坏了，页面本身就打不开了**——
> 建议先把它复制成 `index.html.bak` 再改。

### NTP

启动时**不再阻塞等待**（原来会卡住 app_main 最多 30s）。现在后台异步同步，
状态在 Dashboard 上可见。服务器顺序为 `ntp.aliyun.com` → `cn.pool.ntp.org`
→ `pool.ntp.org`。

> **重要**：`CONFIG_LWIP_SNTP_MAX_SERVERS` 原为 `1`，导致代码里设置的第二个
> 服务器被 lwIP **静默丢弃** —— 实际只试过 `pool.ntp.org`，国内经常连不上，
> 这正是首次开机日志里 `NTP sync timeout after 30s` 的原因。
> 现已改为 `3`，并关闭 `CONFIG_LWIP_SNTP_STARTUP_DELAY`（它会让首个请求
> 随机延迟最多 5s）。这两项在 `sdkconfig.defaults` 里也有记录。

## 性能观测

每一步都会打出一行阶段耗时（同时进串口和任务日志文件）：

```
step 7 timing(ms): total=14210 capture=35 prep=520 (jpeg=310 b64=90 json=120)
                   connect=1840 http=6100 parse=6 sdlog=42 exec=830 sleep=1000
```

| 字段 | 含义 | 看什么 |
|------|------|--------|
| `total` | 本步总墙钟时间 | 唯一的最终指标 |
| `capture` | 等 UVC 帧 + 拷出 | 持续偏大说明采集流水线没跟上 |
| `prep` | 提示词 + JPEG 重编码 + base64 + JSON 序列化 | `jpeg` 占大头就调 `upload_max_dim` |
| `connect` | TCP + TLS 握手 | **为 0 表示复用了长连接**；恒为 1-2s 说明 keep-alive 没生效 |
| `http` | 整个 `perform()` | 减去 `connect` 是服务端推理时间 |
| `parse` | 响应 JSON 解析 | 应该只有个位数 ms |
| `sdlog` | 任务日志落盘 | 偏大说明 SD 卡慢 |
| `exec` | HID 动作执行 | 打字多的步骤会高 |
| `sleep` | `sleep_before_next` | 有下限 1s |

> `connect = 0` 是长连接生效的标志。若它长期非零，说明服务端提前关闭了空闲连接，
> 此时客户端会在下次请求时自动重建。

### 输入法（IME）—— 打字失败的第一嫌疑

在有中文输入法的目标机上，中文模式下的拉丁字母会进入**组字缓冲**而不是目标控件。
按实际危害排序：

| 现象 | 原因 |
|---|---|
| **数字消失** | 组字状态下**数字行是候选词选择键**。`Vicrl-7391-A` 变成 `Vicrl-A` 就是这个——**字母和标点能活下来，数字不能**。这是实测中最高频的一种 |
| **空格消失** | 所有中文输入法里 Space 都是**候选词选择/分词键**，不产生字面空格。`Hello World!` 变 `HelloWorld!` |
| **字母消失** | 被当作拼音解析的一部分，或被候选字母选择键吃掉 |
| **`press "enter"` 像没反应** | 组字状态下**第一个 Enter 只上屏拼音**，需要**第二个 Enter** 才按下对话框默认按钮 |

#### 怎么确定是输入法而不是设备

状态栏会带上一行客观证据：

```
last type: "Vicrl-7391-A" - device queued ALL 12/12 key events, so any
missing/different text on screen was caused by the target machine
```

**只要它说 `ALL N/N`，设备就确实把每一次按键都发出去了**，屏幕上文字不对就是目标机
丢的。串口日志里同一行 `typed 12/12 chars (skipped 0): "Vicrl-7391-A"` 是同样的证据。
看到这个结论就**不要再原样重试**——重试必然再失败。

#### 关键：中英切换是一个**你观察不到的奇偶量**

实测中 agent 在这一步**越修越糟**，原因不是它不够聪明，而是当时的提示词教错了它：

```
2. press "shift" —— MS 拼音中英切换；无效则试 win+space、ctrl+space
```

**微软拼音里 `Shift` 和 `Ctrl+Space` 切换的是同一个状态。** 模型先按 shift（→英文）
再按 ctrl+space（→中文），**切了两次等于没切**，然后在中文模式下又打了一遍。
把两个等价操作并列成"备选方案"，等于在教模型做奇偶抵消。

**但这两个键的可靠性差得很远**（来自 Windows 11 实际使用经验，已写进提示词）：

| 切换键 | 前提条件 | 可靠性 |
|---|---|---|
| `Shift` | **必须有文本光标（caret）** | 低 —— 无焦点时按了没用，**而且待上屏的组合框会把这次 Shift 直接吃掉**，根本轮不到它切换 |
| `Ctrl+Space` | **无视焦点** | 高（约 99%） |

> 这一点直接解释了实测为什么"shift 无效"：那次失败时**组合框正开着**
> （日志里 `'1 A'` 悬在行上）。所以 `Shift` 在这个场景里是**双重不可靠**——
> 既要求 caret，又会被未上屏的组合吞掉。**首选应该是 `Ctrl+Space`。**
> 我最初的提示词把主次写反了。

**`escape` 的作用也要说清**：它不改变中英模式，但**必须先按**——
组合框待上屏时切换键会被吞掉，所以顺序是 `escape` → `ctrl+space`。

#### 探针把"看不见的奇偶量"变成"可观测状态"

这是整个问题的解法核心。**设备读不到输入法模式，但读得到"数字有没有活下来"**：

1. `press "escape"` 然后 `press "ctrl+space"`（可以在同一批）
2. 在**你准备使用的那个控件里**打 2 字符探针 `a1`（`clear_first: true`）
3. 读**应用自己报的字符数**（记事本状态栏写"2 个字符"）
   - `a1` → 模式正确
   - 只有 `a` → 仍是中文
4. 探针完好才清空并打真正的字符串
5. 探针失败就**再切恰好一次**并重新探针；**两次都失败说明这台机器需要换通道**，别再切了

状态栏会报 `IME toggles sent: N`。**N ≥ 2 就是"切换无效"的硬证据**，模型不必再靠猜。

> **设计要点**：奇偶量之所以危险，是因为它**看不见**——每一步都可能是对的也可能是错的，
> 于是模型只能在猜。加一个探针之后，同一个奇偶量就变成了**可测量的状态**，
> 循环自然收敛。这比"再多给几个切换键"有用得多。

#### 但是探针本身也会骗人：必须单独成一步

实测（22:54 那轮）踩了这个坑，而且**代价很大**：

```
#4 action: press "ctrl+space" type "a1" clear_first     ← 切换和探针在同一批
#5 action: press "escape" press "ctrl+space" type "a1" clear_first
#6 action: press "shift" type "a1" clear_first
#7 action: type "<50 词纯字母故事>"                       ← 没有切换，成功了
```

**第 7 步的故事连空格都保住了。** 而中文模式下空格是候选选择键——如果模式还是中文，
故事必然被毁。**所以第 6 步的 `shift` 其实切换成功了**，只是同批的探针在切换生效**之前**
就发出去了，于是给出**假阴性**。

| 结论 | |
|---|---|
| 模式切换在主机侧是**异步生效**的 | 同一批里紧跟切换的按键，可能还是按**旧模式**解释的 |
| 假阴性比"没有探针"更糟 | 它会让你去换一个**本来就不需要换**的通道，每次白烧两个往返 |
| **修正** | 探针**必须单独一步**（跨一次模型往返 ≈4s，足够生效）；提示词已改成"切换后**就此打住，什么都别发，连探针也别发**" |
| 固件保险 | 发完切换键后强制 `vTaskDelay(150ms)`，覆盖"同批里还有别的动作"的情况 |

> 这条也说明了**探针是一把双刃剑**：它把一个不可观测的状态变成了可测量的状态，
> 但如果**测量时机**错了，它会把正确的东西报成错误。
> 所以探针的**时序**和探针本身一样重要。

#### 顺带发现：只吃数字，字母/空格/标点都安全

第 7 步那个 50 词故事（模式仍是中文）**字母、空格、标点全部完好**。
所以当**内容由 agent 自己决定**时（故事、示例消息、占位名、测试串），
**不含数字的内容可以完全绕开这个失败模式**——这比跟输入法周旋划算得多。
但**任务指定的数值不能改**，那是目标本身。

#### 清理已经打进去的错误文字：每个键会破坏什么

**候选窗口开着的时候，组字串还没有进入文档。** 这条界线决定了一切：

| 动作 | 作用范围 | 风险 |
|---|---|---|
| `escape` | **只丢弃组字串，不碰文档** | 无组字串时它会传给应用 → **关闭对话框、取消重命名** |
| `enter` | **提交**组字串（真的写入文档） | 写进去之后还得再删一次，多一个破坏步骤 |
| `backspace` | 组字状态下编辑的是**拼音缓冲**，一次删一个字母、不插入任何东西 | 提交后才删真正的文字。**不能靠它，也不能用它数按键** |
| `ctrl+z` | 撤销上一次编辑 | 一个键，但**作用域不由你控制**：应用的编辑分组方式不同，可能把之前写好的内容一起撤掉。用过之后必须**看**；撤多了用 `ctrl+y` 恢复 |
| `"clear_first": true` | `ctrl+a` = **整个字段** | 空白文档上正确；**字段里已有本任务早先输入的内容时会静默销毁它** |
| `"replace_chars": N` | `shift+left` × N = **恰好最后 N 个字符** | 精确、局部。N 可以从应用自己的字符数算出来（现在 − 输入前） |

> **这解释了为什么问"backspace 还是 enter+ctrl+z"两者都不是首选**：
> `escape` 是唯一**完全不修改文档**的清理动作。`enter` 会把错误文字真正写进去，
> 于是必须再撤销一次，而撤销的作用域不受控。`backspace` 在组字状态下根本删不到文档。
>
> **两个已修的指令缺陷**（都源于上面这张表）：
> 1. 旧提示词写的是"**永远先按 escape**"——无组字串时 escape 会传给应用，
>    在对话框/重命名场景里是破坏性的。现在改成"**仅在候选窗口可见时**先 escape"。
> 2. 旧提示词只有 `clear_first`，而它是**整个字段**。真正多步的任务里
>    （第 1 行打完打第 2 行，第 2 行失败后 clear_first）会把第 1 行一起抹掉。
>    现在补了 `replace_chars`——增量的、局部的替换。

#### 通道实测结果（2026-09-11）

| 通道 | 做法 | 结果 |
|---|---|---|
| 主键盘数字行 | 默认 `type` | ❌ `Vicrl-7391-A` → `Vicrl--A`，**只有 4 个数字消失**，字母和两个连字符全活 |
| **小键盘数字** | `"digits_numpad": true` | ❌ **同样被吃**。`locks=num=on`、`queued=12/12`、通道标记 `keypad` 都在，仍然只剩 8 字符 |

> **小键盘这个假设已经被证伪，不要再试。** 原本指望"输入法只劫持主键盘数字行、放行小键盘"，
> 实测微软拼音把小键盘数字**也**当候选选择键。保留 `digits_numpad` 是因为别的输入法
> （搜狗、QQ 等）可能不同，但它在微软拼音上不是间歇性失败，重试没有意义。
>
> 这个结论能被确认，靠的是 `type` 的动作摘要里现在会记 **通道**
> （`type "..." clear_first keypad`）以及状态栏的 `locks: num=on caps=off`。
> 在那之前，日志里一句 `type "Vicrl-7391-A" clear_first` **无法区分**
> "小键盘也被吃"和"根本没试过小键盘"——**不记录自己跑了哪个变体的实验不是实验。**

**尚未干净测过的一条**：`escape` + `ctrl+space`（一次）之后数字是否就能落地。
之前那次尝试把 escape + shift + 重打放在同一批，随后又按了 ctrl+space（同一个状态的
第二次翻转），所以那个"无效"的结论是被污染的。**这是目前最有价值的下一个实验**——
如果有效，整个问题就归结为"`escape` → 切一次 → 探针验证"，可以修好**任何**应用里的
打字，而不只是这一条字符串。

#### 两种失败长得一样，修法相反

这是调试时最容易走错的一步：

| 症状 | 判据 | 真正的原因 | 修法 |
|---|---|---|---|
| 文字完全没出现 | `screen ... NO - identical` / 动作摘要里的 `[NO SCREEN CHANGE]` | **焦点不在目标控件**（别的窗口或操作者抢走了焦点） | `click` 目标控件内部一次再重打。**切输入法修不了这个** |
| 文字出现了但不对 | 屏幕变了，或应用的字符数变了 | **字符被目标重新解释**（输入法/键盘布局） | 走上面的通道阶梯 |

> 实测踩过：操作者手动点了任务栏的语言指示器去切输入法，焦点离开记事本，
> 于是 `queued=12/12` 而编辑区 `0 个字符`。这**不是**输入法吞字，
> 但当时的提示词把两者混在一起，agent 就会在焦点问题上去切输入法。

#### 不依赖输入模式的绕过方式

顺序的依据：**第 1 条修好的是"任何应用里的打字"，后面几条只修这一条字符串。**

1. **先把模式弄对并验证**：单独发一次 `press "shift"`，然后**看**，再用 `a1` 探针
   读应用的字符数。`a1` 完整到达就说明模式对了，后面一切正常。
   `press "win+space"` 会打开输入法切换浮层，列出所有已安装输入法并高亮当前项——
   那是**大而可读**的覆盖层，很多机器上它是唯一能看到状态的途径。
2. **根本不要往 GUI 里打字。** 字符串只需要落到文件里就用 `run`：
   `{"action_type":"run","command":"cmd /c echo Vicrl-7391-A > C:\\p.txt"}`
   一条动作，没有编辑器。需要看就用 `run "notepad C:\\p.txt"` 以**只读**方式打开。
3. **剪贴板中转。** 把值放到剪贴板再粘贴——`ctrl+v` 是单个原子事件，任何输入法都改不了：
   `run "cmd /c echo Vicrl-7391-A|clip"` → `press "ctrl+v"`
4. **如实报告被阻塞**：以 `done:false` 结束，写明输入法行为、试过哪些通道、操作者可以改什么。

> **待测**：运行对话框（`explorer.exe` 的 Win+R）是否保留数字。剪贴板中转的前提是它保留；
> 这条**还没测过**。判据很干净：如果它也被吃，命令会变成 `cmd /c echo |clip`，
> 粘出来的是 `ECHO is on.` —— 那个输出本身就是答案。
>
> **操作者可以改什么**（不是唯一解，但最省事）：给机器**加一个英文键盘**
> （`设置 → 时间和语言 → 语言和区域 → 添加语言 → English (United States)`）。
> 这样 `win+space` 就有了**可观察的切换浮层**，切换从"看不见的奇偶量"变成"读得出来的状态"。
> 不需要删掉微软拼音。

### 打字与 `run` 动作

**打字是控制通道，不是性能指标。** 掉一个字符的代价是整整一次模型往返加一串恢复
动作，远比省下的几十毫秒贵。所以打字是**刻意拟人化**的，节奏由设备控制：

```json
"hid": {
  "type_hold_ms": 15,          // 按键按住时长
  "type_gap_ms": 35,           // 键间基础间隔
  "type_jitter_ms": 25,        // 每个间隔的随机抖动（避免机械节拍）
  "type_word_pause_ms": 120,   // 空格后的额外停顿（模拟换词）
  "run_dialog_ms": 500,        // Win+R 到对话框可输入
  "run_settle_ms": 150         // 输入完成到回车
}
```

**如果仍然丢字，先调大 `type_gap_ms`。**

#### HID 端点轮询间隔（重要）

描述符里的端点轮询间隔一度是 **10ms**，意味着 host 每 10ms 最多取走一个键盘报告。
当时打字是 8ms 按下 + 4ms 抬起 —— **按下和抬起都落在两次轮询之间，host 从未看见**，
于是周期性丢字（`notepad` 变成 `ntpd`，丢第 2、4、6 位）。现已改为 **1ms**。

同时 `tud_hid_keyboard_report()` 的返回值以前被忽略 —— 端点忙时报告被**静默丢弃**。
现在 `hid_reports.c` 的每个发送都会先 `hid_wait_ready()` 等端点就绪，并在失败时
重试一次、`ESP_LOGW` 报出来。

#### `run` —— 启动程序用一个动作

`run` 自己完成 Win+R → 输入 → 回车，内部延时正确：

```json
{"action_type":"run","command":"notepad","wait_after":1.5}
{"action_type":"run","command":"cmd /c echo hi > C:\\test.txt"}
{"action_type":"run","command":"powershell -NoProfile -Command ..."}
```

现场日志里模型反复卡在"关掉 file not found 对话框 → 重开 Win+R → 全选 → 重打"，
每一步都是一次完整往返。`run` 把这一串变成一个原子动作。

`run` **还会自检**：按下 Enter 后等 700ms 采一次帧指纹，若屏幕**毫无变化**就再按一次
Enter（有界重试，只一次）。这同时覆盖两种真实故障——运行对话框的自动补全下拉吞掉
第一个 Enter，以及输入法组字状态下第一个 Enter 只用于上屏。若第二次仍然没变化，
会打 `ESP_LOGE` 说明命令可能没执行。

`type` 新增 `clear_first`（先按 Ctrl+A），这是修正错误字段的标准做法 ——
比让模型自己编排"点击 → 全选 → 重打"可靠得多。

### 鼠标精度怎么验证

不需要猜是不是偏移问题。状态栏已经上报光标实际位置，只需对比：

1. 让模型 `move` 到某个 `box_2d` 中心，例如归一化 `(0.500, 0.500)`
2. 查状态栏的 `cursor=(...)`

若 `cursor` 与请求一致 → **映射链没问题，精度问题出在模型的视觉定位**。
若系统性偏离 → 检查 `config.json` 的 `output_width/height` 是否就是被控电脑的真实分辨率
（它决定 `pixel_to_abs` 的映射）。把日志级别调到 DEBUG 还能看到
`move px(...) -> abs(...) [screen WxH]`，三段值可以逐一核对。

> 补充：目标机若开启了"提高指针精确度"（鼠标加速），对**绝对坐标**设备不生效，
> 所以那不是嫌疑对象。

### 自适应推理强度（最大的一项延迟杠杆）

实测 Step 1-5 的 `http` 占单步墙钟的 **62–85%**（2653–6191ms），而 `reasoning_tokens`
占输出的 30–50%。也就是说**每一步都让模型深思是最大的可避免开销**。

```json
"api": {
  "reasoning_effort": "low",            // 常规步骤
  "reasoning_effort_escalated": "high", // 卡住时
  "effort_escalate_after": 1
}
```

**"卡住"是客观判定**，harness 本来就知道：

- 上一步动作**没有产生任何屏幕变化**（帧指纹一致）
- 同一种动作类型在最近 15 次里重复 ≥ 4 次

任一成立就计数，连续 `effort_escalate_after` 次后升级到 `high`；**一旦有可见进展
立刻降回 `low`**。串口日志会标明当前用的档位：

```
Step 6: ... | effort=high (escalated) | stuck=2
```

WebUI 的 Dashboard 也能看到当前档位和已卡住的步数。想关掉自适应，把两个值设成一样即可。

### 输出 token 才是账单：给文本字段设预算

实测输出速度约 **116 tok/s**，所以单步墙钟基本就是"输出 token 数 ÷ 116"。而模型默认
会写得很啰嗦——而这些文本**存进轨迹时还会被截断**，多写的部分付了钱却被丢掉。

系统提示里现在明确写了预算（`observation` ≤240 字符、`self_evaluation` ≤200 字符、
`plan_update.summary` 一句话），实测效果：

| | 改前 | 改后 |
|---|---|---|
| Step 1 输出 tokens | 539 | **224（-58%）** |
| Step 1 API 耗时 | 4639ms | **3476ms（-25%）** |
| Step 2 输出 tokens | 568 | **324（-43%）** |
| Step 2 API 耗时 | 3854ms | **3289ms（-15%）** |

同一条提示词还顺带说明了：`plan_update` 里**不要复述目标、状态栏或上一版计划**。

**另一半是任务本身写得含糊**。同一轮测试里第 3 步耗时 **13643ms**，因为 `reasoning_tokens`
飙到 **2326**（占输出 2635 的 88%）—— 那一步的指令在"第 3/4/5 步是否可以合并"上自相矛盾，
模型在推理里反复权衡了十几轮。注意此时 `effort` 仍是 `low`：**推理强度档位管不住
歧义带来的推理膨胀**。指令写清楚比调档位有效得多。

### JPEG 管线：先看三段分解，再决定要不要上 PPA

ESP32-P4 有 **PPA（Pixel Processing Accelerator）**，`ppa_do_scale_rotate_mirror()`
一次就能做完 **裁切 + 缩放 + 旋转 + 镜像**（`in.block_offset_x/y` + `block_w/h` 是裁切，
`scale_x/y` 是缩放），而且文档明确写着 *"the size of the entire picture has no
influence on the performance"* —— **PPA 的耗时只跟裁切块大小成正比**，跟源图大小无关。
理论上这正好对应我们的 ROI 操作。

**但对当前实测路径它没用**，原因在代码里：

```c
resample_region() 里有一条 fast path
    if (dw == cw) { 逐行 memcpy }
```

ROI 请求是 `scale=1`，所以 `cw == dw == 960`，**走的就是这条 memcpy 路径**
（540 行 × 2880 字节 ≈ 1.5MB ≈ 2ms）。PPA 想替代的那一段本来就不是瓶颈。

那 `jpeg=179–207ms` 到底花在哪？**原来的 `compress_ms` 是一个不透明的总数**，
所以这一版把它拆成了四段：

| 字段 | 含义 |
|---|---|
| `setup` | 编解码器引擎/缓冲区建立（**已缓存，稳态应 ≈0**） |
| `dec` | 硬件全分辨率解码 |
| `rs` | 软件裁切 + 盒式缩放（**PPA 唯一能替代的部分**） |
| `enc` | 硬件重编码 |

任务日志的 `Timing(ms)` 行和 WebUI 的耗时柱状图都会显示这四段。

**顺带修掉一个更实在的开销**：原来每一步都在重建整个编解码器链路——

```c
jpeg_new_decoder_engine()              // 每步
jpeg_alloc_decoder_mem(1920*1080*3)    // 每步，6.2MB
jpeg_decoder_process()
jpeg_del_decoder_engine()              // 每步
free(6.2MB)                            // 每步
... 编码器再来一遍 ...
```

采集卡的分辨率整个运行期是恒定的，这些**全部可以摊掉**。现在解码器引擎、解码缓冲区
（6.2MB）、编码器引擎、以及裁切用的暂存缓冲区（grow-only）都缓存在 `jpeg_utils.c` 里，
只在**帧几何变化时**重建。编解码器的内存由一把互斥锁保护（现在只有一个调用方，
但多一个预览路径就会踩坏状态）。

> **PPA 真正的用武之地**：`scale=2/4`（整帧下采样）和 `upload_max_dim>0` 这两条路径
> 走的是逐像素盒式平均，没有 memcpy fast path，那才是软件瓶颈。也就是说
> **PPA 的价值是"让下采样变便宜"**——便宜到 `upload_max_dim` 值得开启，
> 从而把全图步骤的上行从 ~407KB 降到 ~180KB 而**模型看到的信息量完全不变**
> （服务端本来就会缩到 ~1300×731）。
>
> 两个前置条件都已确认：flash 加密**未开启**（PPA 文档里"外部 PSRAM + flash 加密
> 时 SRM 不可用"这条限制不适用），L2 cache line 是 64B（PPA 输出缓冲的对齐要求）。
> 另外 `scale_x/scale_y` 的精度**会被截断到 1/16**，所以它不适合做精确的像素级缩放，
> 但对"缩到模型看得见的尺寸"足够了。

### 上传帧：`upload_max_dim = 0` 表示完全不动

**这是目前推荐的设置。** MS2109 输出的 MJPEG 本身就是完整 JPEG，模型侧也会自行缩放，
所以解码+重编码是纯粹的浪费。

| 值 | 行为 | 代价 |
|---|---|---|
| `0` | **直接透传 MJPEG**，不解码不重编码 | 最省；上传约 150–190KB/步 |
| `>0` | 解码 → 软件盒式下采样 → 重编码 | 全分辨率解码 + ~6MB PSRAM + 软件缩放，换取上传降到约 60KB |

> ⚠️ **`>0` 时的两个坑（已修）**：ESP32-P4 的硬件解码器**不做缩放**，永远输出原分辨率。
> 旧代码按*下采样后*的尺寸分配解码缓冲，导致每次解码都以 `JPEG_ERR_NO_MEM (258)`
> 失败并静默回退到原始帧——`max_dim` 从未生效过。更危险的是：即使缓冲够大，
> 把下采样后的 `width/height` 传给编码器而喂入全尺寸 RGB，编码器只会读
> **左上角一块裁切图**，模型看到的画面缺右下部分，归一化坐标会全部错位。
> 现在解码缓冲按源尺寸（含 16 字节对齐）分配，下采样改在软件里做。

### 设备 Profile

Profile 是**关于这台机器**的短文档，每一步请求都会**全文重新发送**，所以它越长，
每一步的 token 成本和噪声都越高。默认文件是 `sdcard/profiles/win11_laptop.md`，
仓库里已附一份起点版本（系统/分辨率/输入法与切换键/任务栏/常用快捷键）。

**`profile_updates` 的正确用法**：只在学到"下周换一个任务仍然成立"的机器级事实时才写，
**绝大多数步骤应该是空数组 `[]`**。系统提示词里的规则 11 给了明确的正反例。

不该进 profile 的东西（这些都是日志里真实出现过的）：

```
- This machine's Notepad opens with an empty '无标题' document; status bar shows
  line/column and character count, useful for verifying typed text.
- Notepad status bar shows caret line/column and character count — quick way to
  verify exactly typed content.
- Notepad status bar shows character count and caret line/column (e.g. '行 1, 列 7
  12 个字符'), useful to verify typed text length.
```

这三条是**同一件事的三种说法**，而且都是"本次任务里打开 Notepad 才知道的"，不属于
机器档案。它们应该进 `plan_update` / 历史，而不是 profile。

harness 现在有三道防线：

| 防线 | 行为 |
|---|---|
| 提示词规则 11 | 明确列出正例/反例，并要求默认发空数组 |
| **相似度去重** | 归一化后比对已有每一行；完全一致或词包含率 ≥70% 就跳过写入并记日志（专门针对上面这种改写重述） |
| **大小上限** | 文件超过 4096 字节后拒绝追加并告警 |

> 如果你之前的机器上已经生成了 `.md` 这个误命名文件，用 WebUI 的文件页删掉即可。

## 会话（对话窗口）

每个**会话**就是一个独立的上下文窗口：自己的任务目标、计划、以及逐轮**轨迹**。

```
/sdcard/sessions/<id>/
    meta.json        标题、目标、创建时间、步数
    plan.json        该任务的计划与里程碑
    trajectory.txt   逐轮轨迹 —— 模型的记忆
```

- **Start 输入任务** → 新建一个会话窗口
- **会话页点某行** → 切换当前上下文（仅在 IDLE 时允许，避免把 goal/plan 从运行中的任务底下换掉）
- **继续** → 加载该会话并开始运行，步数从原处接着计
- 会话页右侧可以直接**编辑轨迹**，例如删掉跑偏的几步，保存后从下一步生效

### 轨迹里为什么没有历史截图

这是本项目与"通用 Agent 多轮历史"最重要的差别。你说得对——**前缀缓存确实能让历史 token 近乎免费**（命中 $0.006/M vs 未命中 $0.30/M，差 50 倍；实测第 20 步全量历史的费用与现在基本持平，因为输出才是大头）。

**但缓存解决不了字节数。** 一帧 base64 约 160KB，20 步历史就是 **3.2MB，而且每一步都要重传**：

| | 当前 | 带历史截图 |
|---|---|---|
| 每步请求体 | ~160–200KB | 3.2MB（第 20 步）→ 8MB（第 50 步） |
| 设备侧构造 JSON | ~40ms | ~0.8s |
| WiFi 上行 | ~0.2–0.5s | 数秒且线性增长 |
| 决策价值 | — | **零：屏幕早就变了** |

所以设计成：**文本轨迹全部保留**（到 24KB 才裁掉最早的几步，成本可忽略），
**历史截图一张不留**。每步请求里只有当前这一帧。

### 轨迹长什么样

```
#4 [18:31:58] action: click(left,0.450,0.450) type "Hello World!" clear_first
   saw: Notepad is open (title '无标题') ... status bar '行 1, 列 1  0 个字符'
   result: Partially worked: text typed but the space was dropped (11 chars)
   plan: Notepad is open and empty. Click into the editor and type ...
```

相比改动前的两处关键差别：

- **带参数**：`click(left,0.450,0.450)` 而不是只有 `[click]`。模型现在能拿自己发的坐标
  对比状态栏里的光标实际位置，自己判断是不是点偏了。
- **带"看到什么"和"结果如何"**：以前只有一行 `plan_update.summary`，
  模型无法回看自己前几步的判断依据。

### 与 SD 卡任务日志的分工

| | 轨迹（进上下文） | 任务日志（不进上下文） |
|---|---|---|
| 位置 | `sessions/<id>/trajectory.txt` | `log/<id>/<id>.log` + 逐帧 JPEG |
| 内容 | 每轮动作参数/观察/结果/计划 | 完整原始 API 响应 |
| 用途 | 模型决策 | 人排查问题 |

这是书里第 2 章说的"**隔离优于压缩**"：大体积中间信息根本不进主上下文。

### 关于编译优化等级

当前 `sdkconfig` 里是：

```
CONFIG_COMPILER_OPTIMIZATION_DEBUG=y          # -Og + 断言
CONFIG_MBEDTLS_COMPILER_OPTIMIZATION_SIZE=y   # -Os
```

mbedTLS / cJSON / base64 都是 CPU 密集型，在 -Og 下比 -O2 慢数倍。改成
`CONFIG_COMPILER_OPTIMIZATION_PERF`（`idf.py menuconfig` → Compiler options →
Optimization Level → Performance）+ `CONFIG_MBEDTLS_COMPILER_OPTIMIZATION_PERF`
是两处开关，**建议先用上面的计时数据做基线，再改这个开关对比一次**，以免
把"优化等级的影响"和"代码改动的影响"混在一起。

## 视野（ROI 缩放）与画面预览

### 为什么 ROI 不只是"省流量"

关键在服务端的缩放规则：**像素总数低于约 544×544 的图会被放大**，更大的图会被缩小到
总量约等于 1300×1300。所以送整屏和送裁切，拿到的是**不同的有效分辨率**：

| 送什么 | 源像素 | 服务端处理后 | 12px 控件在模型眼里 |
|---|---|---|---|
| 整屏 1920×1080 | 2.07M | 缩到 ~1.69M（≈1734×975） | **~10.8px（认不准）** |
| 裁切 480×270 | 130K | **放大**到 ~296K（≈725×408） | **~18px** |
| 裁切 256×144 | 37K | 放大到 ~296K | **~34px** |

token 上限固定在 ~1024，但**买到的放大倍数从 1.0× 变成 1.5–2.8×**，而且放大在服务端
免费——设备只需裁，不需要插值。这直接对症之前确认过的"鼠标不精确"：映射链没问题，
是模型在小字号上视觉定位不准。

### 模型怎么用

响应里加一个可选字段，作用于**下一次**截图：

```json
"next_view": {"roi": [0.30, 0.25, 0.55, 0.60]}   // ymin,xmin,ymax,xmax，归一化到整屏
"next_view": {"scale": 2}                         // 整屏，缩小一半
"next_view": {}                                   // 回到整屏
```

提示词里明确要求模型**点小目标前、读小字前、点空之后**先要一次放大。

**`next_view` 是粘性的**：不发送就保持当前视野，`{}` 才是显式回到整屏。
一开始实现成"一次性"（每步从 FULL 重新开始），结果模型没重复发送的那一步就静默退回全图——
这是模型从未要求过的状态变化，实测中它发现后困惑了很久，还写了一长段推理来解释。
提示词里"要操作 ROI 以外的区域，先发 `{}` 回到整屏"这句话**本身就预设了粘性**，
代码和提示词当时是不一致的，现已统一为粘性。

粘性也确实是更省的那个选择——实测数据（1920×1080 全图 vs ROI 0.25–0.75）：

| | 全图 | ROI |
|---|---|---|
| `prep` | 318–358 ms | **259 ms** |
| 其中裁切/重编码 | 0 | 197 |
| 其中 base64 | **142–157** | **25** |
| 上行 `Req` | 406 KB | **87 KB** |

裁切+重编码花掉 197ms，但因为 payload 小了 4.7×，base64 一项就省回来 120–130ms，
**净开销几乎为零，还白赚 320KB 上行**。所以"粘着不放"没有代价可担心。

### 坐标映射：唯一可能出错的地方

**`box_2d` 永远是"相对于模型看到的那张图"归一化的。** 状态栏第一段就说明当前视野：

```
view: FULL | step 7/100 | ...
view: ROI y0.300-0.550 x0.250-0.600 scale=1 — box_2d is normalised WITHIN this view | step 8/100 | ...
```

harness 负责反推，只有**一个函数**做这件事（`action_executor.c` 的 `box_to_pixel`）：

```c
full_x = roi_x0 + view_x * (roi_x1 - roi_x0);
```

两个刻意的设计决定：

- **`scale` 完全不需要坐标处理** —— 归一化坐标与分辨率无关，只有 ROI 会移动原点。
  把这条守住，系统偏移就只有一个可能的来源。
- **轨迹里的坐标记的是全局坐标**，另用 `look=` 标注当时看的是哪块区域。
  这样历史跨视野切换仍然可读：
  ```
  #5 [18:32:05] look=ROI(y0.30-0.55 x0.25-0.60 s1) | action: click(left,0.450,0.420)
  ```

### 画面预览 `/api/snapshot`

| 请求 | 返回 |
|---|---|
| `GET /api/snapshot` | **模型实际收到的那张图**（已按 `next_view` 裁切/缩放） |
| `GET /api/snapshot?live=1` | 直接从采集卡抓一帧（实时画面） |

WebUI 的 Dashboard 上有预览面板，显示尺寸（例如 `模型看到的那张 · 725×408`）。
**这是验证 ROI 最直接的手段**——没有它，裁切区域对不对只能靠猜。

### 代价

硬件解码器**不能裁切也不能缩放**，所以每次非整屏视野都要：

```
解码整帧（6.2MB RGB，~150-250ms）→ 裁切 + 软件重采样 → 编码小图（~50ms）
```

但**不能只看这一项**。同一步的实测对比（见上面的表）：ROI 的 `prep` 总计 259ms，
反而比整屏的 318–358ms **更少**，因为 base64 一项就从 ~150ms 掉到 25ms。
裁切的 197ms 是被更大的收益抵消掉的。

所以净账是：**ROI 比整屏更省设备时间，同时省 4.7× 上行**，换来的还有 1.5–2.8× 有效分辨率。
整屏 scale=1 时走无拷贝快路径，不付这个代价。

> **实测时重点看两件事**：预览图的尺寸是否符合预期（`?last` 那张），以及
> 状态栏的 `cursor` 读数是否与模型发的坐标吻合。若系统性偏离，问题就在
> `box_to_pixel` 的映射上——那是唯一改坐标的地方。
>
> **已实测过一次**：模型在 `view: ROI y0.250-0.750 x0.250-0.750` 下发
> `box_2d [0,0,0,0]`，状态栏回到 `cursor=(0.250, 0.250) px=(479,269)`。
> 期望 (0.250,0.250)，**精确命中**；`px` 差 1 像素是 HID 绝对坐标量化的必然结果
> （`(480*32767)/1920 = 8191.75` 截断成 8191，读回 `8191*1920/32767 = 479.99`）。

## need_screen v2 与状态栏

### 状态栏

每条 user 消息开头由**代码**（而非模型）生成一行 `**Status:**`：

```
step 7/100 | cursor=(0.523, 0.411) px=(1004, 444) | held buttons: none |
screen since last screenshot: NO - identical to the screenshot you last saw |
consecutive actions without a new screenshot: 0/3 | recent actions: click x6 of last 15
```

三项都由硬件掌握、模型无法自行得知的信息：

- **`cursor`** —— `hid_device` 精确知道指针位置。截图里指针常常看不清或看不见，
  模型执行一次不带点击的 `move` 后，否则完全不知道自己把光标留在哪。
- **`screen ... NO - identical`** —— 客观回答"我上一个动作到底有没有生效"。
  提示词要求模型自评，但像素级的答案比它的猜测可靠；"没变化"是"点空了"
  最明确的信号。`recent actions: click x6` 则是"你卡住了"的计数器提示。
- **`held buttons`** —— 之前提示词里的 `{pressed_buttons}` 一直被硬编码成 `[]`，
  现在上报真实状态。

### 图像复用（无损）

每步抓帧时用 FNV-1a 对帧数据取指纹。若指纹与**上一张发给模型的帧**完全一致，
说明 JPEG 字节完全相同，于是直接复用上一步已编码好的 base64 —— 跳过压缩与
base64（约 400ms）。这是**可证明无损**的：同指纹 ⇒ 同 JPEG ⇒ 同 base64，
不存在任何"用了陈旧图像"的近似风险。日志会出现：

```
Screen unchanged since last query (182344 bytes); reusing encoded payload
```

### `need_screen: false` 的新语义

**harness 永远重新抓帧**——用旧截图去决定下一个动作是近似，屏幕可能已经变了，
不值得为省 ~35ms 去冒这个风险。

所以 `need_screen: false` 的含义收窄为一个安全得多的请求：
**"我只是在等，屏幕没动之前别再问我了。"** 判定条件是全部满足：

1. 本批动作**全部是 `wait`**（有任何一个 click/press/type/drag 就不成立）
2. 模型给了 `need_screen: false`
3. 帧指纹证明屏幕**仍然**与它最后看到的那张一致
4. 连续跳过次数 < `agent.max_blind_rounds`

满足时直接跳过 API 调用、等待 `wait_settle_ms` 后再比一次；
屏幕一变就立刻恢复询问。`agent.allow_wait_skip` 默认 **false**。

> **默认关闭的原因**：这条路径依赖"静态画面下帧指纹不变"这个前提。MS2109 的
> MJPEG 输出**预期**对静止画面逐帧字节一致，但这一点必须在硬件上确认。
> 打开前请先看日志里是否稳定出现 `Screen unchanged since last query`——
> 若静止画面下从不出现，说明编码器有抖动，此时不应开启。

### 动作空间新增观察

模型现在无需猜测光标位置，也不再需要 `need_screen` 来表达"我要链式动作"——
harness 已不再强制覆盖 `need_screen`（旧代码在 click/press/type/drag 后强置为 1，
与提示词里"chain actions aggressively"直接矛盾）。

## 注意事项

- **MS2109 采集卡**: 必须连接在 USB Host 口（OTG1，GPIO18/19）
- **USB HID 输出**: 连接在 USB Device 口（OTG0，GPIO26/27）
- **SD 卡**: 必须为 FAT32 格式，挂载在 `/sdcard`
- **C6 协处理**: 需要预先烧录 ESP-Hosted 固件
- **内存**: 大量使用 SPIRAM（帧缓存、Base64 编码、HTTP 响应）
- **RTC 时间**: 使用 NTP 同步，时区 UTC+8
- **设备 Profile**: 默认 profile 为 `win11_laptop`，需自行放置 `sdcard/profiles/win11_laptop.md`；
  缺失时模型只会收到一句占位文本，设备操作精度会明显下降
- **滚轮**: 仅支持纵向滚动（`delta_y`）；报告描述符未声明横向滚动字段，
  `delta_x` 会被忽略并在日志中给出警告

### 一个字符搞垮整个任务：JSON 必须是合法 UTF-8

真实踩过的坑，值得单独记一笔。现象：某个中文任务目标下，每一步都是

```
Step 1 | Req: 0B | Resp: 0B | API: 19470ms | Exec: 0ms | parse=0
Response: no response
```

连续 3 次完全一致，然后 `fail_count` 触发中止。看起来像网络或鉴权故障。

**根因**：为了消除 `-Werror=format-truncation`，早先把固定长度拷贝统一改成了
`snprintf(dst, n, "%.*s", n - 1, src)`。但 **`%.*s` 的精度是字节数，不是字符数**——
中文一个字 3 字节，截断点落在字符中间就产生了**非法 UTF-8 字节序列**。

而 HTTP 请求体里的 JSON **必须是合法 UTF-8**，服务端解不出就直接返回 400。于是：

| 观察到的现象 | 真实含义 |
|---|---|
| `http=891~2542ms`、`connect=406ms` | 连上后约 500ms 就被拒——**快速失败**，不是超时 |
| 3 次重试全失败，总耗时 19.5s | 2000+4000+8000 退避 + 每次 ~1.3s，数字完全吻合 |
| `Req: 0B`、`parse=0` | 解析失败导致没有元数据可读，这是**结果不是原因** |
| `prep=243 (b64=122 json=99)` | 请求正常构造完成——所以问题在**内容**，不在流程 |

那条任务目标有 500+ 字节，而 `SESSION_GOAL_LEN` 是 192、`ctx->task_goal` 是 256，
**两处都在字符中间切断了**。之前"打开记事本，输入 Hello World!"只有约 40 字节，
碰不到边界，所以一直没暴露。

**修法（两层）**：

1. `components/storage_manager/utf8_util.h` 提供 `utf8_copy()`，按**字符边界**截断。
   所有面向用户/模型文本的固定长度拷贝都改用它。
2. `cloud_client.c` 在 `cJSON_PrintUnformatted()` 之后对**整个请求体**做一次
   `utf8_sanitize()`，把任何漏网的非法字节替换成 `?`。这是所有请求的唯一出口，
   所以这个不变量是**被强制**的，而不是"相信上游没写错"。

**同一个坑，第二次**：修完上面两处，请求正常了（`Req: 404138B`），但模型做完第 1 步
就 `done: true`，它自己在推理里写道：

> the goal text ends with "?" which suggests the task description may be truncated

原因在上游更远处：`web_server.c` 的 `handle_api_start()` 里是

```c
char task[256] = {0};
strncpy(task, t->valuestring, sizeof(task) - 1);   // 按字节切，而且静默
```

任务目标在**进入 HTTP 层**时就被砍到 255 字节，我在 `agent_start()`/session 里把上限
提到 512 完全没用到。多步中文指令被砍掉了后面的步骤，而 agent **自信地完成了那个更短的
任务**——这比崩溃危险得多，因为没有任何错误信号。

所以现在的规则是：**用户的任务目标超长时"报错"，绝不"截断"**。

```c
if (strlen(t->valuestring) >= sizeof(task)) {
    return send_error(req, 400, "task too long: N bytes, max 1023 (split it into steps)");
}
```

`SESSION_GOAL_LEN` 现在是 1024（约 340 个汉字，足够写出多步指令），并且
`agent_core.c` 里有 `_Static_assert(sizeof(agent_ctx_t.task_goal) == SESSION_GOAL_LEN)`
——这个断言在本次修改中**真的拦下了一次编译**（两边不同步时必然有一处静默截断）。

**排查建议**：遇到"每步都失败且失败得很快"先看**串口日志**（任务日志里没有 HTTP 细节），
找 `HTTP error ... status=400` 和 `Request body: N bytes`。修复后会多打一行
`Request body had N invalid UTF-8 byte(s)`。

**通用教训**：任何一处 `char buf[N]` + `strncpy/snprintf("%.Ns")` 截断用户文本，
都会静默改变语义。截断点可能有好几层（HTTP 边界 → session → agent 上下文），
只修一层不够——优先让每一层都用 `utf8_copy`，并在最外层出口做一次强校验。

### 中止行为

急停（WebUI Emergency / GPIO1 长按）、连续 3 次抓帧失败、连续 3 次 LLM 失败，
这三条路径都会**释放全部 HID 键并回到 IDLE**，而不是终止 agent 任务——
因此设备在急停后仍可通过 WebUI 或 GPIO0 重新开始，无需断电重启。
