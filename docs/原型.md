# 原型 —— Victrl 在 Linux 上的 Python 实现

> **中文** | [English](Prototype.md)

*历史存档。已冻结。不是本仓库的代码。*

在这些东西跑上单片机之前，同一套想法先在一台 PC 上跑过。原型是回答一个问题最便宜的方式：**一个模型看着屏幕的视频采集画面、通过模拟键鼠驱动它，究竟能不能真的把任务做完？** 如果答案是否定的，那为它做硬件就毫无意义。

## 两个实现，并排对比

它们**不是同一份代码库**。第二个是重新实现，不是共享代码的移植。本仓库只包含第二个。

| | **原型** | **当前实现** |
|---|---|---|
| 位置 | Linux PC（Ubuntu） | **ESP32-P4，无操作系统** |
| 语言 | Python | C（ESP-IDF 6.0.1 + FreeRTOS） |
| 画面采集 | `/dev/video0` 上的 V4L2 / OpenCV / ffmpeg | UVC host 驱动，MJPEG 1920×1080 |
| HID 输出 | 串口桥接 → ESP32 BLE HID，或 Linux `uinput` | **原生 TinyUSB 复合设备**（键盘 + 绝对坐标鼠标） |
| 云端调用 | Ark SDK（Doubao-seed） | 无状态 HTTPS，Responses 风格 API |
| 记忆 | 磁盘上的三层（L1 历史 / L2 计划 / L3 设备画像） | SD 卡会话：轨迹 + 计划 + 设备画像 |
| 控制面 | `:8080` 上的 Flask HTTP API | **设备端 WebUI**（仪表板、会话、画面预览、文件浏览） |
| 体积 / 功耗 | 一台 PC | 一块板子、一个采集卡、一张 SD 卡 |
| 状态 | **已冻结，历史存档** | 正在积极开发 |

## 结构

```
┌─ Victrl host: a Linux PC ──────────────────────────────────────────┐
│                                                                    │
│  /dev/video0 ──▶ UvcCapture ──▶ agent.py ──▶ CloudClient ──▶ LLM   │
│  (capture card)   OpenCV/V4L2      │            (Ark SDK)           │
│                                    │                               │
│                                    ├──▶ memory: L1 history          │
│                                    │            L2 plan             │
│                                    │            L3 profile          │
│                                    │                               │
│                                    ├──▶ serial bridge ──▶ ESP32 ──▶ BLE HID
│                                    └──▶ uinput (fallback) ──▶ USB HID
│                                                                    │
│  Flask HTTP API :8080  ◀── control / status                        │
└────────────────────────────────────────────────────────────────────┘
```

| 模块 | 作用 |
|---|---|
| `core/agent.py` | 主回路 |
| `core/cloud_client.py` | 模型调用（Ark SDK，Doubao-seed） |
| `core/uvc_capture.py`、`core/v4l2_direct.py` | 抓帧，两条路径 |
| `core/hid_controller.py`、`core/serial_hid.py` | 键盘/鼠标合成 |
| `memory/short_term.py`、`plan_manager.py`、`profile_manager.py` | L1 / L2 / L3 |
| `utils/coordinates.py` | 归一化 ↔ 像素映射 |
| `api/server.py` | Flask 控制 API |

## 它证明了什么

- **回路是通的。** 采集 → 模型 → JSON 动作 → HID → 重新采集，如此反复，跑的都是真实任务。
- **一个模型可以完全靠像素和一行文本状态栏来驱动。** 在 Windows、Linux、macOS 或 Android 上，都不需要任何形式的目标侧接入。
- **状态应该分三层，而不是一层。** 临时历史、当前计划，以及关于*这台机器*的持久事实，生命周期不同、代价也不同，混在一起只会让 agent 变差。这个结论原封不动地带到了 MCU 版本——今天它就是轨迹、计划和设备画像。
- **脆弱的是 HID 这一侧。** 难点几乎都不在模型上，而在于让按键和点击精确落在它们瞄准的位置。

## 为什么退役

它本身没有任何毛病。它回答了自己的问题，然后就变成了负担：

- **它撑不起这个项目真正的主张。** 一个还需要 PC、一份 Linux 安装和一个串口桥接才能跑的“能自动化任何事情的 AI agent”，说服力要弱得多。真正重要的主张是：这个 agent *就是一台设备*。
- **延迟由往返决定，PC 什么也没带来。** 每一步都是 3–7 秒在等模型。把回路跑在桌面 CPU 上从来就不是瓶颈。
- **两个实现，多了一个。** 让 Python 版本和固件保持同步，意味着每次协议改动、每次提示词改动、每次坐标修正都得做两遍，而烂掉的永远是第二个。

因此原型冻结在它的最后一个版本，仅作参考保留。它的架构不是当前代码的模板；当前代码是从芯片的约束里重新推导出同一套结构的。

## 什么保留了下来，什么没有

| 想法 | 结局 |
|---|---|
| 看见 → 操作 → 观察的回路 | 保留下来，基本没变 |
| 归一化坐标，单一映射函数 | 保留下来，而且更严格了 |
| 三层记忆 | 精神上保留：轨迹 / 计划 / 设备画像 |
| 以文本状态栏为事实基准 | 保留下来并大幅扩展——现在它会报告光标位置、锁定键、屏幕是否变化，以及输入法切换次数 |
| 到 ESP32 的串口 HID 桥接 | **已弃用**——现在 MCU 原生做 HID |
| Flask 控制 API | 被设备端 WebUI **取代** |
| Python 对粗糙资源管理的容忍 | **痛苦地弃用了**——见 [MCU 移植](MCU移植.md) |
