# 输入法问题

> **中文** | [English](Input-Method-Troubles.md)

本项目历史上持续时间最长、代价最高的一次 bug。之所以专门写出来，是因为它的解决方式反直觉，而且它不是 Windows 的某种怪癖，而是一*类*问题：**一条环境有权改写的输出通道。**

## 症状

在中文输入法处于激活状态时，向记事本输入 ASCII 字符串 `Vicrl-7391-A`，得到的结果是 `Vicrl--A`。

这个结果的每一处信息量都很大：

| 证据 | 它说明了什么 |
|---|---|
| `last type: "Vicrl-7391-A" — device queued ALL 12/12 key events` | 设备把每一次击键都发到了线上 |
| 应用程序自己的状态栏显示 `8 个字符` | 12 次按键，8 个字符——正好丢了 4 个 |
| 幸存下来的 8 个是 `Vicrl`、`-`、`-`、`A` | **字母和标点都存活；只有数字被吃掉** |

组字处于打开状态时，**主键盘数字行**上的数字是候选选择键。这一点广为人知。还需要再做一次实验才能确认的是：**小键盘同样会被吃掉**——用主机 LED 报告确认 Num Lock 已开启、12 个按键全部入队的情况下实测，数字依然不见了。那个想当然的绕法（“在小键盘上敲数字，输入法只会劫持数字行”）**对这个输入法并不成立**，代码里保留这个选项，只是因为其他输入法可能不同。

同一批证据还解释了一个更令人意外的现象：**在模式仍为中文时输入的一篇 50 词的英文故事完全正常通过**，空格和标点都没问题。只有数字有风险。

## 为什么它吃掉了一整个任务

模型并不是简单地失败。它是在*一个不断升级的循环里*失败，而这个循环是提示词造成的，不是模型造成的。

当时的规则是这样的：

> 按 `shift` 切换中英文；如果不行，试 `win+space` 或 `ctrl+space`

在微软拼音里，**`shift` 和 `ctrl+space` 翻转的是同一个状态。** 被要求先试一个、再试另一个，模型就切换了两次，正好回到起点——然后在中文模式下把字符串重新敲了一遍，再次失败。

这就是那个可以推广的失败模式：**一个不可观测的奇偶状态，被当成一串备选项递了过来。** 每一次尝试都是 50/50，没有一次是可检验的，模型也根本无从知道自己正在来回摆动。

还有两个细节很重要：

- **`shift` 是条件性生效的。** 只有当文本光标存在时它才会切换，而一个已经打开的组字可能会把它吞掉，而不是执行切换。`ctrl+space` 不需要光标。所以那个备用方案反而比首选方案更可靠。
- **Escape 不是修模式的手段。** 它会丢弃待处理的组字；紧接着的下一个字母又会打开一个新的组字。单独使用它，对中英文状态没有任何改变——但它*必须先做*，因为待处理的组字会把切换吞掉。

## 解决方式

三个想法，按其重要程度排序。

**1. 让不可观测的奇偶状态变得可测量。** 设备读不到输入模式，但它*能*读到某个数字是否存活：

```
press "ctrl+space"          →  (next step, never in the same batch)
type "a1" with clear_first  →  read the application's own character count
   "2 个字符" → mode is right
   "1 个字符" → still Chinese; toggle once more, re-probe
```

两次探测都失败，且探测本身是独立的一步，就意味着这台机器需要另一条通道——停止切换。状态栏还会报告 `IME toggles sent: N`，于是“你已经试过两次了”是一个事实，而不是一段记忆。

**2. 在时间上把探针和切换分开。** 这就是[失败分类学](失败分类学.md)里描述的那个陷阱：三个同批次的探针把一个正常工作的切换报成了坏的。探针必须是独立的一步。

**3. 提供非字符级的通道。** 当任务完全不需要往 GUI 里打字时，不要这样做：

```
run "cmd /c echo <value> > C:\p.txt"     →  no editor, no IME
run "notepad C:\p.txt"                   →  reading needs no typing
run "cmd /c echo <value>|clip"  + ctrl+v →  the payload never traverses the keyboard
```

剪贴板路径是最有希望的一般性答案——`ctrl+v` 是一个原子事件，任何输入法都无法重新解释它——但它还没有被端到端实测过，而且那条把内容放进剪贴板的命令本身也是打出来的，所以它继承了关于“运行”对话框的同一个未决问题。

## 诚实的边界

- **一项确实需要向 GUI 文本框输入数字的任务，如果碰上输入法会吃掉数字的机器，就是被阻塞的。** 这些绕法覆盖的是“把这个值放进文件”和“把这个值粘贴进去”，而不是“把这个数字敲进那个框”。
- **删除中文键盘不是前提条件。** 这是一个合理的部署选择，但不是必需的，把它当成答案会让整个设备都依赖于一台预先准备好的机器。
- **输入法状态可以用眼睛读出来。** 微软拼音会在光标附近画一个 中/英 标记，`win+space` 则会打开一个切换器，列出所有已安装的输入法并高亮当前激活的那个——一个很大、可读的浮层，而且在很多机器上这是唯一能看出状态的办法。agent 被告知要去读它，而不是去猜。

## 仍未解决的问题

1. **在这台机器上，用一个正确分离的探针，`ctrl+space` 能否干净地切换模式？** 此前每一次尝试都被同批次探针或第二次切换污染了。
2. **“运行”对话框会保留数字吗？** 如果会，剪贴板这一跳就成了完整的方案，因为那样载荷永远不会碰到处于输入法激活状态的文本控件。这个测试是自诊断的：如果数字被吃掉，`cmd /c echo |clip` 放到剪贴板上的就会是 `ECHO is on.`，而不是那个值。

两者各自都只需要跑一次很短的测试。
